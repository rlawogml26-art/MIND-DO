# MIND-DO 팀 개발 가이드

> v1 · 최종 업데이트: 2026-10-05
> 이 문서의 규칙은 확정되었고, 규칙을 자동으로 지켜주는 도구(`develop` 브랜치, 브랜치 보호, CI, CODEOWNERS, Issue·PR 템플릿)도 적용되었습니다.
> dev·운영 서버 자동 배포는 **인프라 구축 후** 적용됩니다.
> AI 에이전트용 규칙은 `AGENTS.md`에 따로 있습니다. 작업 전 쓰는 AI 도구에 `AGENTS.md`를 꼭 먼저 읽혀주세요.

---

## 1. 우리 팀이 일하는 방식

이 가이드는 **AI로 코드를 개발한다고 가정했을 때** 지켜야 할 것들을 모아둔 문서입니다. AI 없이 직접 작성하는 경우에도 Issue·Git·PR·리뷰 규칙은 똑같이 적용되고, AI 관련 항목만 해당되지 않습니다.

AI로 개발할 때의 흐름은 다음과 같습니다.

- 작업 지시는 **GitHub Issue**로 받습니다 (AI에게 그대로 넘기는 입력)
- AI는 **AGENTS.md**를 읽고 일합니다 (일하는 방식)
- 결과는 **PR 본문**으로 설명합니다 (AI가 작성, 본인이 읽고 이해한 뒤 제출)

규칙은 문서로만 두지 않고 도구(CI, 브랜치 보호, CODEOWNERS)로 강제합니다. 그래서 규칙을 어기면 병합 버튼이 눌리지 않습니다.

## 2. 역할

| 하는 일                                   | 담당                 |
| ----------------------------------------- | -------------------- |
| 개발 규칙·구조·보안·배포 결정             | 팀장                 |
| 스프린트 운영 (이번 주 할 일, 담당, 기한) | PM (Notion에서 관리) |
| 주간보고서 작성                           | 팀장                 |
| WBS 작성·관리 (교수님 제공 양식)          | PM                   |
| WBS의 작업 순서 검토 (기술적 선후 관계)   | 팀장                 |
| DB 스키마(`schema.prisma`) 수정           | 백엔드 데이터 담당만 |

### PR 승인자 (바꾼 폴더 기준)

| PR이 건드린 곳                                             | 승인자             |
| ---------------------------------------------------------- | ------------------ |
| `backend/`                                                 | 팀장               |
| `backend/prisma/` (DB 스키마)                              | 백엔드 데이터 담당 |
| `shared/`                                                  | 팀장               |
| `frontend/`                                                | PM                 |
| `AGENTS.md`, `.github/`, ESLint·tsconfig 등 루트 설정 파일 | 팀장               |

- PR이 여러 폴더를 건드리면 해당하는 승인자 **모두**의 승인이 필요합니다.
- 승인자는 GitHub가 자동으로 리뷰어로 지정합니다 (CODEOWNERS).

- DB에 컬럼·테이블이 필요하면 직접 고치지 말고 **Issue로 데이터 담당에게 요청**합니다. "어떤 테이블에 무엇이 왜 필요한지" 한 줄이면 됩니다.
- 규칙·설정 파일을 바꾸고 싶으면 PR로 제안할 수 있습니다. 이런 PR은 팀장의 승인이 있어야 병합할 수 있습니다.

## 3. 작업 흐름

1. PM이 이번 주 할 일·담당·기한을 정합니다.
2. 담당자는 AI로 **Issue 템플릿**(할 일 / 완료 기준 / 건드리지 말 것)을 채워 Issue를 올립니다.
3. 승인자가 Issue 방향을 확인합니다.
4. `develop`에서 작업 브랜치를 만들고, Issue 내용을 AI에게 넘겨 작업합니다.
5. 작업이 끝나면 AI가 PR 본문을 작성합니다. **본인이 읽고 이해한 뒤** PR을 올립니다.
6. PR 본문에 `Closes #이슈번호`를 적어 Issue와 연결합니다. (연결할 Issue가 없는 작업이면 그 줄을 지웁니다)
7. 승인자가 리뷰하고 승인합니다.
8. CI ✅와 필요한 승인이 모두 붙으면 **PR 작성자가 직접 병합합니다** → dev 서버에 자동 배포 (자동 배포는 인프라 구축 후)
   - 승인을 받은 **뒤에** 커밋을 추가하면 승인이 자동으로 취소됩니다. 다시 승인을 받아야 병합할 수 있습니다.
   - 병합 버튼은 사람이 직접 누릅니다. AI에게 병합을 맡기지 않습니다.

### PR 규칙

- **작게**: 기능 하나, 대략 300줄 이내. 넘으면 나눠서 올립니다.
- **PR 본문 필수**: 무엇을 / 왜 / 어떻게 확인했는지
- **CI ✅인 PR만 리뷰합니다.** ❌가 뜨면 에러 메시지를 AI에게 주고 고친 뒤 다시 올립니다.
- "왜 이렇게 했는지"는 PR 본문에 씁니다. 코드 주석은 코드만 봐서는 이유를 알 수 없는 곳에만 답니다.
- **PR 제목은 커밋 규칙과 같은 `타입: 내용` 형식으로 씁니다.** (예: `feat: 회원가입 API 추가`) 병합되면 PR 제목이 develop의 커밋 한 줄로 남습니다.

## 4. AI 사용

> **AI를 사용하지 않고 직접 코드를 작성하는 경우 이 섹션은 해당되지 않습니다.** 나머지 규칙(작업 흐름, Git, 폴더 구조, 코드 규칙, 보안)은 그대로 적용됩니다.

1. **AI 도구는 자유입니다.** 어떤 AI를 써도 됩니다.
2. **작업을 시작할 때 AI가 `AGENTS.md`를 읽은 상태여야 합니다.**
   - 레포 안에서 코드를 직접 고치는 도구는 대부분 이 파일을 알아서 읽습니다. (Claude Code는 `CLAUDE.md`, Gemini CLI는 `GEMINI.md`를 통해 `AGENTS.md`를 읽도록 연결해 두었습니다)
   - 웹에서 대화하는 채팅형 AI는 대화를 시작할 때 파일을 첨부하거나, 프로젝트 지침 기능에 등록합니다.
   - 어느 쪽인지 모르겠으면 그냥 첨부하면 됩니다.
3. **Issue 내용을 통째로 AI에게 넘깁니다.** 자기 말로 다시 풀어서 전달하면 내용이 빠지거나 바뀝니다.
4. **PR을 올리기 전에 AI에게 "이 코드가 뭘 하는지 설명해줘"라고 묻고, 이해한 뒤 올립니다.** 이해하지 못한 코드를 올리면 리뷰에서 설명할 수 없고, 학기가 끝나도 남는 게 없습니다.

## 5. Git 규칙

### 브랜치

| 브랜치           | 역할                                                   | 어디로 병합                    |
| ---------------- | ------------------------------------------------------ | ------------------------------ |
| `main`           | 운영 서버 (멘토 앞 시연용). 하나뿐                     | -                              |
| `develop`        | dev 서버. 검토를 통과한 코드만 모이는 합본. 하나뿐     | `main` (팀장이 화요일 배포 시) |
| `feature/기능명` | 새 기능 작업. 기능마다 새로 만들고, 병합되면 자동 삭제 | `develop`, **Squash merge**    |
| `fix/내용`       | 버그 수정 작업. 위와 같음                              | `develop`, **Squash merge**    |

- 이름은 영어 소문자와 하이픈만: `feature/signup`, `fix/login-token`
- `main`, `develop`에는 직접 push할 수 없습니다. 반드시 작업 브랜치 → PR로 들어갑니다.
- 작업 브랜치는 항상 최신 `develop`에서 만듭니다.

### 커밋 메시지

형식: `타입: 내용` (한국어 가능) · 예: `feat: 회원가입 API 추가`

| 타입     | 의미        |
| -------- | ----------- |
| feat     | 기능        |
| fix      | 버그        |
| refactor | 구조 개선   |
| docs     | 문서        |
| chore    | 설정·패키지 |

### 병합

- 작업 브랜치 → `develop`: **Squash merge** (PR의 커밋들을 하나로 합쳐 병합)
- `develop` → `main`: 팀장이 배포할 때만 진행합니다.

## 6. 폴더 구조

```
MIND-DO/
  backend/     API 서버
  frontend/    앱
  shared/      프론트·백엔드가 함께 쓰는 코드 (zod 스키마 등)
```

### backend

**지켜야 할 것 (확정)**

- 기능마다 폴더 하나를 둡니다. (예: `auth/`, `ticket/`)
- 기능 폴더 안에서 세 역할을 나눕니다: **요청 처리**(받기·검증·응답) / **판단 로직** / **DB 저장·조회**
- 호출은 한 방향으로만: 요청 처리 → 판단 로직 → DB 저장·조회
- DB(Prisma) 호출은 **DB 저장·조회 역할에만** 둡니다.
- 다른 기능의 데이터가 필요하면 **그 기능의 판단 로직(service) 함수를 가져다 씁니다.** 다른 기능의 테이블을 직접 조회하는 코드를 새로 짜지 않습니다. 같은 코드가 두 벌이 되면 한쪽만 고쳐지는 사고가 나고, 비밀번호 해시처럼 빼야 할 정보가 새어나가기 쉽습니다.

**기본 설정 (팀장이 만들어 둠)**

- `backend/package.json`, `backend/tsconfig.json`, `backend/src/server.ts`는 이미 있습니다. 백엔드 뼈대는 이 위에 만듭니다.
- `backend/tsconfig.json`은 루트의 `tsconfig.base.json`을 물려받습니다. 팀 공통 타입 규칙(strict)이 여기서 옵니다.
- **`src/server.ts`는 서버 시작 파일입니다.** 배포할 때 이 파일이 실행되므로 이름과 위치를 바꾸지 않습니다.
- `package.json`의 `build`, `start`, `typecheck` 명령 이름은 CI와 배포가 쓰므로 바꾸지 않습니다. 개발용 명령(예: `dev`)은 뼈대에서 추가합니다.

**폴더 위치 (확정)**

```
backend/
  prisma/              DB 스키마·마이그레이션 (데이터 담당)
  src/
    modules/
      기능명/          기능마다 폴더 하나 (예: auth, ticket)
        (파일들)        ← 이름과 구성은 담당자가 정함
```

- `backend/prisma/`와 `backend/src/modules/기능명/` 위치는 바꾸지 않습니다.
- **기능 폴더 안의 파일 이름과 구성은 그 파트 담당자가 정합니다.** 위의 세 역할만 나뉘어 있으면 됩니다.
- 단, 먼저 만들어진 기능 폴더의 이름 방식을 이후 기능 폴더도 따릅니다. (AI도 기존 폴더를 보고 맞춥니다)

참고용 예시 (이대로 할 필요 없음):

```
auth/
  auth.routes.ts       주소 연결
  auth.controller.ts   요청 받기, 검증, 응답
  auth.service.ts      판단 로직
  auth.repository.ts   DB 저장·조회
```

- 공통 미들웨어·설정 위치 등은 백엔드 뼈대 PR에서 정해 이곳에 추가합니다.

---

### shared

프론트와 백엔드가 **둘 다 알아야 하고, 둘이 반드시 같아야 하는 것**만 둡니다. 따로 적으면 어긋나서 버그가 납니다. (예: 앱은 사진 5장 허용, 서버는 3장 허용 → 업로드 실패)

| 넣는 것                                | 넣지 않는 것                                                    |
| -------------------------------------- | --------------------------------------------------------------- |
| zod 스키마 (입력 검증)                 | 비밀값 (앱에 같이 설치되어 누구나 볼 수 있음)                   |
| 제한 숫자·상수 (사진 개수, 글자 수 등) | 한쪽에서만 돌아가는 코드 (Prisma, bcrypt, React Native 화면 등) |
| API 요청·응답 타입                     | Prisma가 만든 타입                                              |

- API 응답 타입은 **Prisma 타입을 가져오지 말고 따로 정의합니다.** Prisma 타입에는 비밀번호 해시 같은 필드가 들어 있고, 앱에 Prisma가 딸려 들어가게 됩니다.
- `shared/`가 바뀌면 프론트·백엔드가 동시에 영향을 받으므로 팀장이 승인합니다.

## 7. 개발 환경과 패키지

### 개발 환경

- **Node는 24 버전**을 씁니다. 터미널에서 `node -v`를 쳐서 `v24`로 시작하는지 확인하세요. 다른 버전이면 `npm install`이 거부됩니다.
- 패키지 매니저는 **npm만** 씁니다. yarn, pnpm은 쓰지 않습니다.

### 처음 레포를 받았을 때

```
git clone https://github.com/rlawogml26-art/MIND-DO.git
cd MIND-DO
npm install
npm run build -w shared
```

모든 명령은 **레포 맨 위(루트)**에서 실행합니다.

**커밋 이메일 숨기기 (권장)**: 우리 레포는 Public이라 커밋에 적힌 이메일이 누구에게나 보입니다. GitHub → Settings → Emails에서 "Keep my email addresses private"를 켜고, 거기 나오는 `숫자+아이디@users.noreply.github.com` 주소를 등록하세요.

```
git config --global user.email "복사한 noreply 주소"
```

### 자주 쓰는 명령

| 명령                      | 하는 일                                      | 언제                                |
| ------------------------- | -------------------------------------------- | ----------------------------------- |
| `npm run format`          | 코드 모양 자동 정리                          | PR 올리기 전                        |
| `npm run lint`            | 코드 규칙 검사 (`any` 사용 등)               | PR 올리기 전                        |
| `npm run typecheck`       | 타입 검사                                    | PR 올리기 전                        |
| `npm run build -w shared` | `shared/`를 변환해 백엔드·앱이 쓸 수 있게 함 | `shared/`를 고친 뒤                 |
| `npm run dev -w shared`   | `shared/`를 고칠 때마다 자동으로 다시 변환   | `shared/`를 계속 고치는 동안 켜두기 |

**PR을 올리기 전에 `format` → `lint` → `typecheck`를 순서대로 돌려 모두 통과하는지 확인하세요.** CI가 똑같은 검사를 하기 때문에, 여기서 실패하면 PR이 병합되지 않습니다.

### 패키지 설치 규칙

- **설치는 레포 맨 위(루트)에서, 대상 폴더를 지정해서 합니다.**
  ```
  npm install express -w backend
  npm install zod -w shared
  ```
  팀 전체가 같은 방식으로 설치해야 어느 폴더에 무엇이 들어갔는지 헷갈리지 않습니다. (Expo처럼 폴더 안에서 따로 설치를 돌리는 도구는 그 폴더에 lock 파일을 만들 수 있으니, 폴더 안에 `package-lock.json`이 생기면 지우고 루트에서 `npm install`을 다시 합니다)
- **`package-lock.json`은 루트에 하나만 두고 반드시 커밋합니다.** 팀원 모두가 정확히 같은 버전을 설치하게 해주는 파일입니다.
- 필요한 패키지는 설치해도 됩니다. 대신 **PR 본문에 패키지 이름과 추가한 이유를 적습니다.**
- **설치 전에 npm 사이트(npmjs.com)에서 진짜 있는 패키지인지 확인합니다.** 주간 다운로드 수가 충분한지 보면 됩니다. AI는 존재하지 않거나 이름만 비슷한 가짜 패키지를 추천할 수 있고, 그런 이름을 노린 악성 패키지도 실제로 있습니다.
- 같은 역할의 패키지가 이미 있으면 새로 추가하지 않습니다.
- Prisma 7, zod 4 등 고정된 기술은 버전을 바꾸지 않습니다.
- `.npmrc` 파일에 토큰 같은 비밀값을 넣지 않습니다. (레포에 올라가는 파일입니다)

## 8. 코드 규칙

### API 응답 형식 (모든 API 공통)

```json
// 성공
{ "data": { "userId": 12, "email": "a@b.com" } }

// 실패
{ "error": { "code": "EMAIL_ALREADY_EXISTS", "message": "이미 가입된 이메일입니다." } }
```

- 성공이면 `data`, 실패면 `error` 중 하나만 옵니다.
- 앱은 `error.code`를 보고 판단합니다. `message`는 화면 표시용이라 문구가 바뀔 수 있으니 판단에 쓰지 않습니다.
- 에러 코드 목록은 `shared/`에 있습니다. 새 실패 상황이 생기면 백엔드가 목록에 추가합니다.

### HTTP 상태 코드

| 코드 | 뜻            | 예                                   |
| ---- | ------------- | ------------------------------------ |
| 200  | 성공          | 티켓 조회                            |
| 201  | 새로 만들어짐 | 회원가입, 티켓 생성                  |
| 400  | 요청이 잘못됨 | 비밀번호가 너무 짧음 (zod 검증 실패) |
| 401  | 로그인 필요   | 토큰 없음, 만료                      |
| 403  | 권한 없음     | 남의 티켓 수정 시도                  |
| 404  | 없음          | 존재하지 않는 티켓                   |
| 409  | 충돌          | 이미 가입된 이메일                   |
| 500  | 서버 오류     | 코드 버그, DB 연결 실패              |

- 502·503·504는 서버가 꺼져 있거나 응답이 늦을 때 AWS(ALB)가 대신 돌려주는 값입니다. 이때는 `error` 모양이 아닐 수 있으므로, **앱은 상태 코드 숫자를 먼저 보고** 500번대는 전부 "잠시 후 다시 시도해주세요"로 처리합니다.

### 이름

- API로 주고받는 필드 이름은 camelCase입니다: `userId`, `createdAt`
- 그 외 이름 규칙은 각 파트에서 정하고, 코드 모양은 Prettier가 자동으로 맞춥니다.

### 타입

- `any`를 쓰지 않습니다. 모르면 `unknown`을 쓰고 확인 후 사용합니다.
- 타입 에러를 `@ts-ignore`나 `as`로 덮지 않고 원인을 고칩니다.
- 이 규칙은 CI가 자동으로 검사합니다.

## 9. 보안

### 가장 흔한 사고: 주소만 바꿔서 남의 티켓 보기

내 티켓이 `/tickets/37`이면 남의 티켓은 36이나 38입니다. 서버가 "이 티켓을 이 사람이 볼 수 있나"를 확인하지 않으면, 숫자만 바꿔서 남의 비공개 티켓을 보거나 **수정·삭제**할 수 있습니다. 내 계정으로 테스트하면 정상으로 보여서 잘 발견되지 않습니다.

### 열람 권한

| 공개 범위 | 볼 수 있는 사람    |
| --------- | ------------------ |
| 비공개    | 주인만             |
| 친구공개  | 주인 + 주인의 친구 |
| 전체공개  | 누구나             |

- 수정·삭제는 공개 범위와 상관없이 **주인만** 할 수 있습니다.
- 볼 수 있는지 판단하는 함수는 티켓 쪽에 **하나만** 두고, 티켓을 보여주는 모든 API가 그 함수를 거칩니다.

### 사진

사진은 서버를 거치지 않고 CloudFront로 바로 열리기 때문에 별도로 보호합니다.

- 파일 이름은 무작위 문자열로 저장합니다. (순서 번호 금지)
- 사진 주소는 **시간 제한 링크**로 줍니다. 서버가 열람 권한을 확인한 사람에게만 잠깐 열리는 주소를 발급하므로, 링크가 퍼지거나 공개 범위를 바꿔도 시간이 지나면 열리지 않습니다.
- 서명에 필요한 키와 사용법은 인프라 쪽(팀장)에서 제공합니다.

### 기본 규칙

| 규칙                                                                                                                                                        | 안 지키면 생기는 일                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **비밀값(DB 비밀번호, JWT 비밀키, AWS 키)을 코드에 쓰지 않는다.** 환경변수로만 읽고 `.env`는 커밋하지 않는다. 필요한 변수는 `.env.example`에 이름만 적는다. | 우리 레포는 Public입니다. 커밋되는 순간 전 세계에 공개되고, 지워도 기록에 남습니다. AWS 키는 봇이 몇 분 안에 가져가 크레딧을 다 쓰고 추가 요금까지 나옵니다. |
| **실제 키·비밀번호를 AI 채팅창에 붙여넣지 않는다.**                                                                                                         | 외부 서비스에 비밀값이 남습니다.                                                                                                                             |
| **앱과 `shared/`에는 비밀값을 넣지 않는다.** (`EXPO_PUBLIC_` 변수 포함)                                                                                     | 앱 파일은 열어보면 안의 문자열이 다 보입니다.                                                                                                                |
| **바깥에서 들어온 데이터는 서버에서 zod로 검증한다.**                                                                                                       | 앱에서만 막으면, 앱을 거치지 않고 요청을 직접 보내 제한을 우회할 수 있습니다. (예: 사진 5장 제한 우회)                                                       |
| **로그에 비밀번호·토큰·개인정보를 남기지 않는다.** 요청 내용을 통째로 찍지 않는다.                                                                          | 서버 로그는 오래 남고 여러 사람이 볼 수 있습니다.                                                                                                            |
| **서버 오류(500) 응답에 상세 에러를 담지 않는다.** 상세 내용은 서버 로그에만 남긴다.                                                                        | DB 구조와 서버 폴더 구조를 공격자에게 알려주게 됩니다.                                                                                                       |
| **비밀번호는 해시해서 저장한다.** 원문을 저장하지 않고, 응답에도 해시값을 넣지 않는다.                                                                      | DB가 유출되면 사용자들이 다른 사이트에서 쓰는 비밀번호까지 털립니다.                                                                                         |
| **앱은 로그인 토큰을 `expo-secure-store`에 저장한다.** AsyncStorage에 저장하지 않는다.                                                                      | AsyncStorage는 암호화되지 않아, 휴대폰 파일에 접근할 수 있으면 토큰이 그대로 보이고 남이 내 계정으로 로그인할 수 있습니다.                                   |

### 아직 정하지 않은 것

- **로그인 토큰의 유효 기간과 갱신 방식**: PM·백엔드·프론트가 함께 정할 예정입니다. 정해지기 전까지 임의로 구현하지 말고 팀장·PM에게 확인해주세요.
  - 함께 정하는 이유: 토큰을 짧게(예: 1시간) 유지하면 털려도 피해가 짧지만 사용자가 자주 다시 로그인해야 하고, 이를 피하려면 "토큰 갱신" 기능이 필요합니다. 갱신은 백엔드가 갱신 API를 만들고 프론트가 만료될 때마다 자동으로 갱신 요청을 보내야 해서 양쪽 작업이 함께 생깁니다. 길게(예: 30일) 유지하면 구현은 단순하지만, 털리면 그 기간 동안 남의 계정으로 쓸 수 있습니다. 결국 "사용자가 얼마나 자주 로그인하게 할 것인가"라는 사용 경험(기획) 문제이면서 백엔드·프론트 작업량이 달라지는 문제라 PM·백엔드·프론트가 함께 정합니다.

## 10. 주간 일정

| 요일 | 할 일                                                                             |
| ---- | --------------------------------------------------------------------------------- |
| 화   | **스프린트 마감**. 팀장이 dev 서버 확인 후 운영 서버 배포 (배포는 인프라 구축 후) |
| 수   | 팀장 주간보고서 작성, 다음 스프린트 시작                                          |
| 목   | (발표 주) 운영 서버 리허설, 버그 수정만                                           |
| 금   | (격주) 발표                                                                       |

- 화요일까지 PR이 병합되어야 그 주 배포에 들어갑니다.
- 발표 주 목·금은 **배포 동결**: 버그 수정 외에는 운영 서버에 반영하지 않습니다.

## 11. 문서 관리

| 문서                  | 위치                 | 관리 | 내용                       |
| --------------------- | -------------------- | ---- | -------------------------- |
| 팀원 가이드 (이 문서) | 레포 `docs/`         | 팀장 | 역할, 흐름, 규칙과 그 이유 |
| `AGENTS.md`           | 레포 맨 위           | 팀장 | AI가 따르는 규칙           |
| 스프린트 운영         | Notion               | PM   | 이번 주 할 일, 담당, 기한  |
| WBS                   | Notion (교수님 양식) | PM   | 전체 작업 계획             |

### WBS 작성 방법

1. **PM**이 교수님 양식으로 WBS를 관리합니다.
2. **팀장**이 작업 순서를 검토합니다. 예: User 테이블이 회원가입보다 먼저, 인프라가 dev 서버 배포보다 먼저
3. 매주 스프린트는 WBS에서 이번 주 몫을 꺼내 정합니다.

### 새로운 결정이 나면

1. **서기**가 Notion 회의록에 결정 사항을 정리합니다.
2. **팀장**이 그 내용을 보고 팀원 가이드와 `AGENTS.md`에 반영합니다. (스프린트·WBS 관련 결정은 PM이 Notion에 반영)

- 문서 수정은 팀장만 합니다. 바꾸고 싶은 내용이 있으면 누구든 팀장에게 제안할 수 있습니다.
- 회의에서 정했더라도 문서에 반영되기 전까지는 AI가 모릅니다. 반영 전에는 옛 규칙대로 코드가 만들어질 수 있으니, 급한 결정은 팀장에게 바로 알려주세요.

## 12. 알아두면 좋은 개념

### 폴더 vs 브랜치

레포에는 `backend/`, `frontend/`, `shared/` 폴더가 있습니다. 폴더는 "코드가 어디에 있냐", 브랜치는 "레포 전체의 어느 버전이냐"입니다. 모든 브랜치에 세 폴더가 다 들어 있습니다.

### develop vs feature

`develop`은 팀 전체의 합본이고, `feature`는 한 사람이 한 기능을 만드는 일회용 작업 공간입니다. develop에서 직접 작업하면 미완성 코드가 다른 사람과 dev 서버를 망가뜨리기 때문에, 항상 feature에서 작업하고 PR로 합칩니다.

### CI (자동 검사)

PR을 올리면 GitHub가 자동으로 코드를 검사하고 결과를 ✅ / ❌로 표시합니다.

- lint: ESLint로 코드 규칙 위반 검사 (`any` 사용, 안 쓰는 변수 등)
- 타입 검사: TypeScript로 데이터 모양이 맞는지 검사
- 모양 검사: Prettier 규칙대로 정리됐는지 검사 (`npm run format`을 안 돌리면 여기서 걸림)

❌인 PR은 병합할 수 없습니다. 참고로 병합 후 서버에 자동으로 올리는 건 CD(배포)라고 부르고, CI와 CD 모두 GitHub Actions에서 돌아갑니다.

### ESLint, tsconfig

CI가 검사할 때 쓰는 기준 파일입니다. ESLint는 코드를 어떻게 쓰는지, tsconfig는 타입을 얼마나 엄격하게 볼지 정합니다. **에러를 없애려고 이 파일의 규칙을 끄면 안 됩니다.** 그래서 이 파일들은 팀장 승인 없이는 바뀌지 않게 막혀 있습니다.

### CODEOWNERS

"이 폴더를 바꾸는 PR은 이 사람이 승인해야 한다"를 적은 파일입니다. PR이 건드린 파일을 보고 GitHub가 담당자를 자동으로 리뷰어로 지정하므로, 누구에게 리뷰를 받을지 따로 신경 쓸 필요가 없습니다.

### Squash merge

PR 안의 여러 커밋("수정", "다시 수정" 등)을 하나로 합쳐 병합하는 방식입니다. develop에는 PR 하나당 한 줄만 남고, 세부 과정은 PR 안에 그대로 남아 있습니다.
